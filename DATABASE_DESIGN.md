# RELATIONAL DATABASE DESIGN & NORMALIZATION SPECIFICATION
## Urban Disaster Response & Relief Coordination Platform (UDRRMS / UDR-ORP)

---

## 1. Relational Database Overview

The UDRRMS data layer is implemented as a 3NF relational database. The schema is defined in Oracle Enterprise SQL (`database/01_udrrms_oracle_schema.sql`) and mirrored in SQLite (`database/udrrms.db`) for lightweight portable deployment.

- **Total Tables**: 27 Normalized Tables
- **Normalization Level**: Third Normal Form (3NF) across all entities
- **Integrity Constraints**: Primary Keys, Foreign Keys with Cascade rules, NOT NULL, UNIQUE, and CHECK constraints
- **Indexes**: 16 dedicated B-Tree performance indexes on join foreign keys and predicate columns
- **Views**: 4 enterprise reporting views for high-speed executive dashboards

## 2. Table Inventory by Functional Domain

### Domain 1: Authentication & Role-Based Access Control (RBAC)
1. `ROLES`: System access roles (`CITIZEN`, `DISASTER_OFFICER`, `COORDINATOR`, `FIELD_RESPONDER`).
2. `USER_ACCOUNTS`: User credentials, bcrypt password hashes, contact details, role foreign key.
3. `CITIZEN_PROFILES`: Citizen medical notes, emergency contacts, blood group, address.
4. `USER_SESSIONS`: Active JWT sessions, client IP, user agent, expiration timestamps.

### Domain 2: Incident Management & Disaster Triage
5. `DISASTER_TYPES`: Standard hazard taxonomy (`FLOOD`, `FIRE`, `EARTHQUAKE`, `CYCLONE`, `STRUCTURAL_COLLAPSE`).
6. `DISASTERS`: Official verified disaster incidents (`INC-YYYYMMDD-XXXXXX`), severity level (`P1` to `P4`), status, activated/closed timestamps.
7. `DISASTER_REPORTS`: Citizen-submitted emergency alerts (`RPT-YYYYMMDD-XXXXXX`), casualties, trapped count, medical/evacuation flags, geocoded coordinates.
8. `REPORT_UPDATES`: Chronological supplemental updates added by reporting citizens or officers.
9. `INCIDENT_MEDIA`: Image attachments, evidentiary field photos, MIME type, storage URIs.
10. `LOCATIONS`: Geographic reference points, ward numbers, hazard zones (`CRITICAL`, `HIGH`, `MODERATE`), latitude/longitude coordinates.

### Domain 3: Rescue Operations & Tactical Deployment
11. `RESPONSE_TEAMS`: Rescue units (`NDRF 10th Bn Alpha Squad`, `EMS Trauma Unit`), specialized capabilities, readiness status.
12. `TEAM_MEMBERS`: Individual responders, rank, certification, phone.
13. `MISSIONS`: Tactical deployment orders (`MIS-YYYYMMDD-XXXXXX`), target incident, assigned team, operational status (`ASSIGNED`, `EN_ROUTE`, `ON_SCENE`, `COMPLETED`).
14. `MISSION_LOGS`: Operational diary entries, milestone timestamping, casualty extraction tallies.
15. `VEHICLES`: Emergency fleet units (ambulances, zodiac inflatable rafts, rescue trucks, de-watering pumps).

### Domain 4: Supply Chain, Warehouse Logistics & Inventory
16. `WAREHOUSES`: Regional disaster supply depots (Hebbal Central, Manyata Vault, Yelahanka North), pallet capacity, depot manager.
17. `RESOURCES`: Master supply catalog (inflatable boats, 50L medical oxygen, 72hr food ration kits, potable water, trauma kits).
18. `INVENTORY`: Multi-depot stock balances, on-hand quantity, reserved quantity, reorder threshold, unit of measure.
19. `INVENTORY_TRANSACTIONS`: Immutable ledger tracking stock intake, reservations, allocations, and dispatches.
20. `RESOURCE_REQUESTS`: Incident supply requirements (`REQ-YYYYMMDD-XXXXXX`), requesting mission/incident, urgency priority.
21. `REQUEST_ITEMS`: Line items for each resource request, requested quantity, approved quantity.
22. `RESOURCE_ALLOCATIONS`: Transactional stock reservation orders linking inventory balances to approved requests.
23. `DELIVERIES`: Dispatch manifests (`DSP-YYYYMMDD-XXXXXX`), transport vehicle, transit status (`DISPATCHED`, `IN_TRANSIT`, `DELIVERED`), confirmation signatures.

### Domain 5: Evacuation Camps, Medical Facilities & Audit
24. `SHELTERS`: Evacuation relief camps (stadiums, community halls, government schools), maximum capacity, current occupancy count.
25. `EVACUEE_REGISTRATIONS`: Individual displaced persons checked into shelters, family size, check-in timestamp.
26. `HOSPITALS`: Emergency trauma centers, total ICU beds, available general beds, ambulance triage desk.
27. `AUDIT_LOGS`: Append-only audit trail capturing actor user ID, action verb, target table, prior state, new state, and ISO timestamp.

## 3. Schema Definitions & Table Specifications

### 3.1 Table: `DISASTER_REPORTS`
```sql
CREATE TABLE DISASTER_REPORTS (
    report_id NUMBER GENERATED BY DEFAULT ON NULL AS IDENTITY PRIMARY KEY,
    report_reference_id VARCHAR2(30) NOT NULL UNIQUE,
    reported_by_user_id NUMBER NOT NULL,
    disaster_type_id NUMBER NOT NULL,
    location_id NUMBER NOT NULL,
    description CLOB NOT NULL,
    people_affected NUMBER DEFAULT 1 NOT NULL CHECK (people_affected >= 0),
    injuries_reported NUMBER DEFAULT 0 NOT NULL CHECK (injuries_reported >= 0),
    missing_persons NUMBER DEFAULT 0 NOT NULL CHECK (missing_persons >= 0),
    trapped_persons NUMBER DEFAULT 0 NOT NULL CHECK (trapped_persons >= 0),
    urgent_medical_needed CHAR(1) DEFAULT 'N' NOT NULL CHECK (urgent_medical_needed IN ('Y', 'N')),
    evacuation_needed CHAR(1) DEFAULT 'N' NOT NULL CHECK (evacuation_needed IN ('Y', 'N')),
    status VARCHAR2(25) DEFAULT 'SUBMITTED' NOT NULL 
        CHECK (status IN ('SUBMITTED', 'AWAITING_INFORMATION', 'VERIFIED', 'DUPLICATE', 'REJECTED')),
    verified_by_user_id NUMBER NULL,
    verified_at TIMESTAMP NULL,
    rejection_reason VARCHAR2(500) NULL,
    latitude NUMBER(9,6) NOT NULL,
    longitude NUMBER(9,6) NOT NULL,
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP NOT NULL,
    CONSTRAINT fk_dr_user FOREIGN KEY (reported_by_user_id) REFERENCES USER_ACCOUNTS(user_id),
    CONSTRAINT fk_dr_type FOREIGN KEY (disaster_type_id) REFERENCES DISASTER_TYPES(type_id),
    CONSTRAINT fk_dr_loc FOREIGN KEY (location_id) REFERENCES LOCATIONS(location_id),
    CONSTRAINT fk_dr_verifier FOREIGN KEY (verified_by_user_id) REFERENCES USER_ACCOUNTS(user_id)
);
```

### 3.2 Table: `INVENTORY`
```sql
CREATE TABLE INVENTORY (
    inventory_id NUMBER GENERATED BY DEFAULT ON NULL AS IDENTITY PRIMARY KEY,
    warehouse_id NUMBER NOT NULL,
    resource_id NUMBER NOT NULL,
    quantity_available NUMBER DEFAULT 0 NOT NULL CHECK (quantity_available >= 0),
    quantity_reserved NUMBER DEFAULT 0 NOT NULL CHECK (quantity_reserved >= 0),
    reorder_threshold NUMBER DEFAULT 10 NOT NULL CHECK (reorder_threshold >= 0),
    unit VARCHAR2(20) NOT NULL,
    last_updated TIMESTAMP DEFAULT CURRENT_TIMESTAMP NOT NULL,
    CONSTRAINT uq_wh_resource UNIQUE (warehouse_id, resource_id),
    CONSTRAINT fk_inv_wh FOREIGN KEY (warehouse_id) REFERENCES WAREHOUSES(warehouse_id) ON DELETE CASCADE,
    CONSTRAINT fk_inv_res FOREIGN KEY (resource_id) REFERENCES RESOURCES(resource_id) ON DELETE CASCADE
);
```

### 3.3 Table: `RESOURCE_ALLOCATIONS`
```sql
CREATE TABLE RESOURCE_ALLOCATIONS (
    allocation_id NUMBER GENERATED BY DEFAULT ON NULL AS IDENTITY PRIMARY KEY,
    request_id NUMBER NOT NULL,
    inventory_id NUMBER NOT NULL,
    quantity_allocated NUMBER NOT NULL CHECK (quantity_allocated > 0),
    allocation_status VARCHAR2(20) DEFAULT 'PENDING' NOT NULL 
        CHECK (allocation_status IN ('PENDING', 'DISPATCHED', 'COMPLETED', 'CANCELLED')),
    allocated_by_user_id NUMBER NOT NULL,
    allocated_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP NOT NULL,
    CONSTRAINT fk_alloc_req FOREIGN KEY (request_id) REFERENCES RESOURCE_REQUESTS(request_id),
    CONSTRAINT fk_alloc_inv FOREIGN KEY (inventory_id) REFERENCES INVENTORY(inventory_id),
    CONSTRAINT fk_alloc_user FOREIGN KEY (allocated_by_user_id) REFERENCES USER_ACCOUNTS(user_id)
);
```

## 4. Normalization Analysis (1NF, 2NF, 3NF)

### 4.1 First Normal Form (1NF) Compliance
- **Atomic Attributes**: Every column holds a single atomic value. No composite fields or multi-value arrays are stored in a single column (e.g. `injuries_reported`, `trapped_persons`, `missing_persons` are separate numeric columns).
- **Unique Records**: Every table is defined with an explicit single-column surrogate Primary Key (`user_id`, `report_id`, `inventory_id`, etc.) generated by database sequences/identities.
- **No Repeating Groups**: Repeating collections such as team members, line items, supplemental updates, and evacuees are factored into dedicated child tables.

### 4.2 Second Normal Form (2NF) Compliance
- A table is in 2NF if it is in 1NF and every non-key attribute is fully functionally dependent on the primary key.
- In junction tables (such as `INVENTORY` with candidate key `(warehouse_id, resource_id)`), surrogate keys `inventory_id` are designated as primary keys, and non-prime attributes (`quantity_available`, `quantity_reserved`, `reorder_threshold`) depend on the complete combination of warehouse and resource, not a subset.
- Line items in `REQUEST_ITEMS` depend fully on the composite identification of the line item and parent request.

### 4.3 Third Normal Form (3NF) Compliance
- A table is in 3NF if it is in 2NF and no non-prime attribute is transitively dependent on the primary key ($X \rightarrow Y$ and $Y \rightarrow Z$).
- **Transitive Dependency Elimination**: In `DISASTER_REPORTS`, the location name, ward name, and risk zone are not stored directly in the report table. Instead, a foreign key `location_id` references the `LOCATIONS` table. This prevents update anomalies where changing a ward name would require mutating multiple report records.
- In `INVENTORY`, the resource description, supplier name, and category are not duplicated from `RESOURCES`. Instead, the inventory row only stores warehouse-specific stock levels and foreign keys.

### 5.2 Enterprise Dashboard Views
```sql
-- View: Real-time inventory balances and threshold alerts
CREATE OR REPLACE VIEW V_INVENTORY_STATUS AS
SELECT 
    i.inventory_id,
    w.warehouse_id,
    w.warehouse_name,
    w.city,
    r.resource_id,
    r.resource_name,
    r.category,
    i.quantity_available,
    i.quantity_reserved,
    (i.quantity_available + i.quantity_reserved) AS total_on_hand,
    i.reorder_threshold,
    i.unit,
    CASE 
        WHEN i.quantity_available = 0 THEN 'OUT_OF_STOCK'
        WHEN i.quantity_available <= i.reorder_threshold THEN 'CRITICAL_LOW'
        ELSE 'OPTIMAL'
    END AS stock_status,
    i.last_updated
FROM INVENTORY i
JOIN WAREHOUSES w ON i.warehouse_id = w.warehouse_id
JOIN RESOURCES r ON i.resource_id = r.resource_id;
```

## 6. ACID Transaction Management

All inventory allocations and state transitions enforce ACID semantics:
```python
# Atomic stock reservation in FastAPI / SQLAlchemy
def allocate_stock(db: Session, request_id: int, inventory_id: int, qty: int, user_id: int):
    with db.begin():
        inv = db.query(Inventory).filter(Inventory.inventory_id == inventory_id).with_for_update().first()
        if not inv or inv.quantity_available < qty:
            raise HTTPException(status_code=400, detail="Insufficient warehouse inventory balance")
        
        # Deduct available and add to reserved atomically
        inv.quantity_available -= qty
        inv.quantity_reserved += qty
        
        # Record allocation
        alloc = ResourceAllocation(
            request_id=request_id,
            inventory_id=inventory_id,
            quantity_allocated=qty,
            allocation_status="PENDING",
            allocated_by_user_id=user_id
        )
        db.add(alloc)
        
        # Write to immutable audit ledger
        audit = AuditLog(
            user_id=user_id,
            action="ALLOCATE_STOCK",
            entity_name="INVENTORY",
            entity_id=inventory_id,
            details=f"Reserved {qty} units for Request #{request_id}"
        )
        db.add(audit)
```
If an unhandled exception or constraint violation occurs during any step, the transaction automatically rolls back, preventing negative inventory or orphaned allocation records.
